## Question
Does prefixing each chunk with an LLM-generated statement situating it inside its own
article — indexing the prefixed text while the generator still sees the original chunk —
improve retrieval over the dense control?

## Configuration diff
```yaml
# vs configs/promoted.yaml
+ axis: assembly
  chunker: contextual                # was: fixed_token
  chunker_params:
    chunk_size: 600                  # unchanged — the control's boundaries
    overlap: 100                     # unchanged
+   context_model: openai/gpt-oss-20b   # DEC-064
+   context_max_words: 60
```
One dimension. The chunk **boundaries are the control's**, so this isolates the prefix
rather than confounding it with a re-chunk the way every Axis 1 chunker did. Only
`Chunk.text` (indexed) carries the prefix; `context_text` stays the original chunk, so
the generator's input is unchanged and only retrieval can move.

The single failed call was `EmptyGenerationError` — `gpt-oss-20b` spent 210 reasoning

indexed as the control's chunk, instead of the whole run. That is MIS-034's hardening
doing exactly the job it was written for, one run after it was written.

## Observations

**The pre-registered sub-hypothesis was right about where and wrong about whether.**
H-022 said that if the effect were real it should concentrate in chunks from
multi-chunk articles, because 79% of articles are a single chunk and for those the
prefix restates text the chunk already contains. Splitting the 200 dev questions by
whether their gold article is multi-chunk:

| Subset | n | Control | This run | Δ | gained / lost |
|---|---|---|---|---|---|
| Gold article is **multi-chunk** | 100 | 0.660 | 0.670 | **+0.010** | 12 / 11 |
| Gold article is **one chunk** | 100 | 0.780 | 0.780 | **+0.000** | **4 / 4** |

The one-chunk half is **perfectly inert** — four questions up, four down, delta exactly
zero. That is a clean mechanistic confirmation: where the prefix summarises an article
the chunk already contains in full, it changes nothing whatsoever. All the movement is
in the multi-chunk half, exactly as predicted, and it amounts to +0.010 with 12 gained
against 11 lost.

**And the dev split is enriched for the case that should have worked.** 21.0% of corpus
articles are multi-chunk, but **50.0%** of dev questions have a multi-chunk gold article
— longer articles attract more questions. So this test ran on a subset 2.4x enriched for
the condition the technique needs, and still returned +0.010.

**Where it works, it works by supplying vocabulary the question uses and the chunk does
not.** *"do I have to give my login to a website designer to work on my site"* — gold
moved from outside the top 5 to **rank 1**. The chunk is about seats and invitations;
the generated prefix reads *"…how to invite collaborators to a Wix website using the
Roles & Permissions dashboard, covering invitation steps, seat limits…"*. The question
contains neither "collaborator" nor "permissions"; the prefix bridged them. Two more
gains have the same shape: *"restore the selection of projects for my Wix collection"*
(>5 → 4 and 5, prefix names "backs up collections… restore a backup") and a Google
indexing question (>5 → 5).

**The losses are the reason the net is zero, and they are not bad prefixes.**
*"how to add more static pages to a Wix website"* fell from **rank 1 to outside the top
5**, and its gold prefix is entirely accurate: *"how to add a new page in the Wix
Editor, covering the steps for creating blank or template pages and the available page
types."* Nothing went wrong with that document. What changed is that **every competing
document also got a prefix**, so the lift is roughly uniform across the index and
relative ordering barely moves. A technique that improves every candidate equally cannot
re-rank them. That is consistent with the contingency table — 16 gained, 15 lost — and
with the one-chunk subset's exact 4/4.

**Same depth shape as the rerankers, from a completely different mechanism.** Better at
the top (@1 +0.035), flat at 5, worse at depth (@10 −0.020, @20 −0.025). EXP-0024 and
EXP-0025 produced that profile by re-ordering a fixed candidate set; this run produced it
by changing what is indexed. Three techniques, two mechanisms, one shape. Worth noting
that recall@20 fell by 0.025 here, so the prefix demonstrably moves some golds *down* out
of the deeper bands, which a purely additive "more findable" story would not predict.

## Anomalies
The one failed prefix call **succeeded on the warm repeat**, so `run_20260925_051847_7c33`
reports 8,218 prefixes generated while reusing the index built by the cold run, which
contains 8,217 prefixed chunks and one unprefixed. One chunk in 8,218 (0.012%) cannot
move a metric, and the headline run is the cold one whose index matches its own chunks
exactly. It does expose that **`chunker_id` is not a complete identity for an
LLM-built index** — a retry that succeeds later changes the indexed text without changing
the key. Recorded as OQ-043.

`rag compare` warns on both runs that the pipeline called an LLM (DEC-049). On the cold
run the cache backed 16% of calls; on the repeat, 99.99% — never exactly 100%, because
the one permanently-failing call is not cached, so the warning cannot be cleared by
repetition. The warning is reported here as preflight 24 requires.

## Scale honesty
This is the most expensive experiment in Phase 2 and it is still only **$0.25**, because
the corpus is 6,221 articles and 8,218 chunks. The same technique on 6 million documents
is one LLM call per chunk at the same unit rate: roughly **$250 per index build**, repeated
on every re-chunk, every prompt revision and every model change. It is bounded and
affordable here and would be a standing budget line there. That difference is part of the
finding, not a footnote to it.

## Decision
**Control retained; not promoted.** Δ +0.005 at p = 1.000 on the deciding metric, +0.010
on the warm repeat at p = 0.857, and +0.010 on the enriched multi-chunk subset it was
supposed to help.
