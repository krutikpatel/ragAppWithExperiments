# EXP-0031 — Query decomposition

- **Status:** VALID
- **Date:** 2026-09-25
- **Run IDs:** `run_20260925_062204_6667` (cold, 3% cache) and
  **`run_20260925_063044_0da8`** (warm, 100% cache — the headline, per P2-03)
- **Git SHA:** 0c00edb (`git_dirty=0` on both)
- **Split:** `dev`, Tier 1, all 200 questions
- **Compared against:** `promoted` = EXP-0005 dense control, `run_20260912_225005_be04`
- **Cost:** $0.00226 cold, **$0.00009** warm. 50 s of LLM wall-clock (200 questions
  prewarmed at 16 workers).
- **Hypothesis:** H-023, written before the run.

## Question
Does splitting a question into the sub-questions it depends on, retrieving for each and
fusing by RRF, improve retrieval — particularly on multi-document questions?

## Configuration diff
```yaml
# vs configs/promoted.yaml
+ axis: query_transform
+ query_transform: decompose
+ query_transform_params:
+   model: openai/gpt-oss-20b      # DEC-065
+   max_parts: 4
```
The original question is **not** retrieved for; the sub-questions replace it. A question
the model judges indivisible comes back as one line, and that line is what gets searched.

## What the transform did
| | |
|---|---|
| Questions | 200 · **zero fallbacks**, zero failed calls |
| Mean sub-questions per question | **1.27** (254 generated in total) |
| Questions actually split (≥2) | **50 of 200** |
| Of the 150 unsplit, returned **verbatim** | **145** |
| New documents per extra sub-query | **40.8** (at retrieval depth 100) |

## Results
Paired bootstrap + McNemar (`rag compare`, DEC-047), 200 questions, seed 20260915.
The **warm** run is the headline: its 100% cache hit rate is what makes the paired
test's fixed-outcome assumption hold (P2-03). The cold run is reported alongside it
because the difference between them is a measurement in its own right.

| Metric | Control | Warm run | Δ | 95% CI | p | Contingency |
|---|---|---|---|---|---|---|
| **strict recall@5** | **0.7200** | **0.6650** | **−0.0550** | **[−0.095, −0.015]** | **0.0186** | **4 gained / 15 lost** |
| strict recall@1 | 0.3050 | 0.3100 | +0.0050 | [−0.035, +0.045] | 1.000 | 8 / 7 |
| strict recall@10 | 0.8500 | 0.8200 | −0.0300 | [−0.065, +0.005] | 0.152 | 3 / 9 |
| strict recall@20 | 0.9200 | 0.9000 | −0.0200 | [−0.050, +0.005] | 0.293 | 2 / 6 |
| nDCG@10 | 0.6308 | 0.6132 | −0.0177 | [−0.049, +0.013] | 0.266 | 15 / 26 |

Per slice, strict recall@5 (warm): `gold_docs:single` 0.8125 → **0.7562** (−0.0563,
**p = 0.0347**, n=160); `gold_docs:multi` 0.3500 → **0.3000** (−0.0500, p = 0.628,
n=40); `q_len:long` 0.7742 → 0.6613 (−0.1129, **p = 0.0405**, n=62).

**The cold run gave −0.0450 at p = 0.0501 / McNemar 0.0490** — straddling the
threshold. Both are reported rather than the convenient one. The 0.010 gap between two
runs whose transforms were byte-identical (100% cached) is hosted query-embedding
non-determinism (OQ-023), the same 0.005–0.010 seen in EXP-0030.

## Observations

**The entire loss is in the 50 questions that were actually split.**

| Subset | n | Control | This run | Δ | gained / lost |
|---|---|---|---|---|---|
| Not split (1 query) | 150 | 0.713 | 0.707 | **−0.007** | 1 / 2 |
| **Split (≥2 sub-queries)** | **50** | **0.740** | **0.540** | **−0.200** | **3 / 13** |

The unsplit 150 reproduce the control, as they should: 145 of them were returned
verbatim, so the control's query was searched. This is a clean internal control and it
means the technique is not diluting everything — **it is specifically destroying the
questions it acts on.** Those questions were not harder to begin with: their control
recall was 0.740, *above* the unsplit group's 0.713.

**The sub-queries genuinely retrieve different documents, and that is the problem, not
the fix.** Each extra sub-query found **40.8 documents** that no earlier sub-query had.
I expected the opposite — that two sub-questions about one task would pull back the same
articles and RRF would reproduce the control. It does not. The decomposition works
exactly as designed and the design is wrong for this corpus.

**Why: the gold article answers the whole question, and each part has a better match
that is not the gold.** Four of the thirteen losses, with the sub-questions the model
produced:

- *"How can I add a personalized name to my automated emails? I was advised to use
  dynamic values."* → *"…personalized name to automated emails in Wix?"* +
  *"…use dynamic values in Wix automated emails?"* — **gold rank 1 → 10.**
- *"how to reconnect a domain without affecting email after accidentally changing the
  CNAME record"* → *"…after accidentally changing the CNAME record?"* +
  *"…without affecting email services?"* — **gold rank 1 → 19.**
- A PDF/CMS question split into updating a PDF in a collection + *"How do I enable
  sandbox collections and sync them with live collections?"* — a sub-topic the model
  inferred rather than found. **Gold rank 2 → beyond 20.**
- A Google Search Console question — gold rank 4 → 6.

Both sub-questions in each case are good questions. Each has its own best-matching
article, and that article is not the gold. RRF then ranks *"best answer to part A"* and
*"best answer to part B"* above *"good answer to both"*, because RRF reads only ranks:
a document at rank 1 of one list beats a document at rank 3 of two lists at k=60.

**This is a statement about how the corpus is organised, not about the technique.**
Decomposition assumes documents are indexed by sub-fact, so that assembling an answer
means collecting parts. A help centre is organised **by task**, and a user's multi-part
question is usually one task — "add a personalised name using dynamic values" is one
article, not two. Splitting it asks the index for something it does not contain.

**The multi-document slice, which this technique was ordered first to serve, went down.**
0.350 → 0.300, three questions lost and one gained (p = 0.628, n=40, so not
distinguishable from noise on its own). It is the fourth technique in this project aimed
at multi-document questions — after MMR, reranking and contextual retrieval — and the
fourth not to move it.

## Anomalies
`q_len:long` is the worst-hit slice (−0.1129, p = 0.0405) and that is mechanical rather
than mysterious: longer questions are the ones with enough content to split, so they
carry most of the 50.

## Hypothesis
H-023, written before the run. **Wrong on both halves, and wrong about the part I
flagged as most uncertain — which turned out to be the mechanism.**
1. I predicted `multi_doc` would improve by **more than +0.05**. It fell by 0.050.
2. I predicted overall recall would **not move**, because most questions would not be
   split. The premise held — 1.27 sub-questions, 150 of 200 unsplit — but the conclusion
   did not: 50 questions moving by −0.200 is enough to move a 200-question split by
   −0.055 at p = 0.019.
3. I wrote that the part I expected to be wrong was "that the sub-queries retrieve
   *different* documents", and named `distinct_doc_yield_per_query` as the number I
   cared about most. It came back at **40.8 new documents per extra sub-query** — they
   retrieve very different documents indeed. I had it inverted: I treated high yield as
   the success condition, when it is the failure condition. Retrieving 41 documents that
   answer half the question is how the one document that answers all of it gets pushed
   out of the top five.

## Decision
**Control retained; not promoted.** Significant and negative on the deciding metric.
